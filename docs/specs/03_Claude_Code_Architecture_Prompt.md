# Claude Code への依頼プロンプト（2作品共通）

次の文章をClaude Codeに貼り付ける。作業ディレクトリには `01_Demon_Summoner_GDD.md` と `02_Lifetime_Roguelike_GDD.md` が存在する前提。最初は**設計だけ**を依頼する。

---

あなたは経験豊富なインディーゲームのテクニカルディレクター、Godot 4アーキテクト、ゲームプレイエンジニアです。

下記の2つのMarkdown仕様書を読み、Steam向けWindows PC用の2D見下ろし型ローグライトを**それぞれ独立したプロジェクト**として開発するための、現実的なアーキテクチャ設計を行ってください。

- `01_Demon_Summoner_GDD.md`: 魔王自身が逃げながらモンスターを召喚・指揮するゲーム。
- `02_Lifetime_Roguelike_GDD.md`: 寿命をHP・通貨・スキルコスト・借金の担保にするゲーム。

## 最初にすること
1. 両仕様書の矛盾、未決定事項、複雑すぎる部分、面白さを損なう可能性を洗い出し、重要度順に整理する。
2. 不明点は致命的でない限り仮定を置いて設計を進め、「採用した仮定」として記録する。
3. Godot 4系 / GDScriptを第一案とする。別技術の方が明確に優位な場合は根拠とトレードオフを提示する。
4. 2ゲーム間の共通化はアイデア・設計原則にとどめ、MVPでは無理に共通ライブラリや巨大なモノレポを作らない。

## 各ゲームについて必ず出力するもの
- `docs/architecture.md`: シーン構成、ノードツリー、責務分担、状態遷移、イベント/シグナル、依存関係、データフロー、主要処理フロー（Mermaid図歓迎）。
- `docs/folder_structure.md`: 実際に利用できるGodotプロジェクトのフォルダ/ファイル構成案と主要ファイルの役割。
- `docs/data_schema.md`: Resource / JSONのどちらで管理するか、その理由、具体的なサンプル定義、バリデーション方針。
- `docs/gameplay_systems.md`: 入力、プレイヤー移動、戦闘、召喚または寿命、敵AI、ウェーブ/部屋生成、強化、UI、セーブ/設定。
- `docs/performance.md`: 更新ループ、敵や召喚獣の大量処理方針、計測方法、最適化の優先順位、劣化時の対策。
- `docs/test_plan.md`: 単体/統合/手動テスト、仕様書の受け入れ条件と対応するテストケース。
- `docs/milestones.md`: 1人開発前提の縦切りスライス（vertical slice）→MVPへの順序、依存関係、完了条件、リスク。
- `docs/decisions.md`: 技術選択、仮定、保留判断のADR形式ログ。

## 必須の具体的検討
### Demon Swarm
- 魔王は自分で移動して回避するが通常攻撃しない。
- 敵は基本的に魔王を狙う。召喚獣の妨害に反応するAIをシンプルに成立させる。
- 召喚時の位置補正、味方の当たり判定、移動/密集、命令対象の選択、ターゲットの失効を扱う。
- MVP60味方＋80敵を想定して60FPS目標を検証するための計測設計。1000体対応は将来目標とし、MVPで保証しない。
- 将来の部隊進化を実装しやすいように、アップグレード効果の重ね掛け、召喚定義、種族タグを疎結合にする。
### Life Debt
- 残寿命の増減を一元管理する。tick、被弾、購入、借入、返済、上限/ゼロの一貫性を守る。
- UIポーズ時の時間停止と、ゲーム進行時の時間減少の扱いを定義。
- 契約の満期判定、滞納、回収人、差し押さえ、清算を状態機械として定義。
- 部屋遷移と債務処理のイベント順序、二重実行防止、ゲーム終了との競合を明記。
- シードと乱数の責務を定義し、少なくともマップ・敵出現・報酬を再現可能にする。

## アウトプットの形式
1. まず2作品を横並びで比較した**アーキテクチャ決定サマリー**と最大リスクを提示。
2. その後、プロジェクトを `demon_swarm/` と `life_debt/` に分け、各フォルダ以下に上記8つの設計ファイルを作成。
3. 未解決事項は `docs/open_questions.md` にゲームごとに最大10件記載し、推奨デフォルトを添える。
4. 最初の実装スプリントでは「最小の動く縦切りスライス」に限定し、具体的なタスクをそれぞれ最大12項目に分割。
5. 最後に、ユーザーが実行できるGodot 4導入・プロジェクト起動・デバッグ方法をWindows向けにまとめる。

**この依頼ではアーキテクチャと実装計画だけを作成し、ゲーム実装はまだ行わないでください。** 仕様書に重大な矛盾がある場合は、修正案を提示し、元ファイルは勝手に上書きしないこと。
